# Solveng: 50 additional operation and modifier bugs/gaps

Audited 2026-10-29 against the current tree and `docs/gap-audit-50.md`. These findings are intentionally separate from B01–B22 and F23–F50. They are an audit backlog, not fixes. N01–N25 are numeric/array boundary findings; N26–N50 cover numerical conditioning, operation contracts, and modifiers/solving.

## Numeric and array findings

| ID | Reproduction / affected operation | Expected behavior | Current gap / evidence |
|---|---|---|---|
| N01 | `0^0 =` | Reject as undefined or report an explicit domain result. | `simp_pow` returns `1` for every zero exponent before zero-base validation (`core/src/expr.rs`, `simp_pow`). |
| N02 | `f(x):=exp(ln(x)); f(0) =` | Domain error inherited from `ln(0)`. | `exp(ln(x))` simplifies to `x`, losing the inner logarithm's domain restriction (`core/src/expr.rs`, `simp_f`). |
| N03 | `ln(e^(2*pi*#i)) =` | Principal `ln(1) = 0`. | `ln(e^x)` is rewritten to `x` without a branch check, yielding `2πi` (`core/src/expr.rs`). |
| N04 | `cos(arccos(x)) ->` | Prove/simplify to `x` on the principal continuation. | Only the sine/arcsine composition is recognized; cosine/arccosine has no corresponding identity (`core/src/expr.rs`). |
| N05 | `tan(arctan(x)) ->` | Prove/simplify to `x` on the principal continuation. | Tangent/arctangent composition is not simplified (`core/src/expr.rs`). |
| N06 | `sinh(asinh(x)) ->` | Provide the inverse-hyperbolic operation and simplify the composition. | No `asinh`/`acosh`/`atanh` operation or inverse-hyperbolic representation exists (`core/src/builtins.rs`, `expr.rs`). |
| N07 | `sinc(0.5 + 1e-16) =` | Stable value with continuous numerical accuracy across the threshold. | The implementation switches abruptly from a fixed series to direct `sin(z)/z` at `|z| = 0.5` (`core/src/eval.rs`, `cardinal`). |
| N08 | `sinc(1e-200) =` | Return approximately `1` without underflow or avoidable loss. | The fixed ten-term series has no error/underflow control and does not establish a conditioning bound (`core/src/eval.rs`). |
| N09 | `tanc(0.5 + 1e-16) =` | Stable result near the series/direct-evaluation boundary. | The same hard threshold switches to `tan(z)/z`; near poles this can amplify rounding without a diagnostic (`core/src/eval.rs`). |
| N10 | `factorial(171) =` | Explicit overflow/domain diagnostic or a documented continuation policy. | Numeric factorial stops at 170, while the derivative path uses a logarithmic approximation, giving inconsistent operation domains (`core/src/expr.rs`, `eval.rs`). |
| N11 | `factorial(3.0) =` after an approximate calculation | Preserve integer factorial semantics when the value is exactly integral. | Exact integer folding is restricted to integer-valued `Num`; float-valued integral inputs take a different approximate path (`core/src/expr.rs`). |
| N12 | `mean(vec(1e308, 1e308)) =` | Return `1e308` or report a controlled finite-range error. | The reduction sums the raw values before dividing, so the intermediate sum overflows (`core/src/linalg/mod.rs:454–457`). |
| N13 | `min(vec(0, 1 V))` versus `median(vec(0, 1 V))`. | Define one consistent policy for dimensionless zero mixed with dimensioned values. | `median`/numeric reductions allow a unitless zero through `common_dimension`, while `min`/`max` require exact `Dim` equality and reject it (`core/src/numerics.rs:51–56`, `core/src/linalg/mod.rs:459–462`). |
| N14 | `variance(vec(1e15,1e15+1,1e15+2))` | Preserve the representable unit-scale spread, approximately `1`. | Values are converted to `f64` before centering; centering cannot recover distinctions already rounded away (`core/src/numerics.rs`). |
| N15 | `stdev(vec(1e15,1e15+1,1e15+2))` | Approximately `1`. | Same pre-centering `f64` conversion loses the input increments (`core/src/numerics.rs`). |
| N16 | `linterp(vec(1e16,1e16+2),vec(0,2),1e16+1)` | Return `1` when the query lies halfway between knots. | Knot/query conversion to `f64` can erase the spacing, causing endpoint selection or a zero denominator (`core/src/numerics.rs`). |
| N17 | `linfit(vec(1e16,1e16+1,1e16+2),vec(1,2,3))` | Recover slope `1` with a correctly translated intercept. | Input conversion to `f64` loses unit-scale x differences before the centered regression (`core/src/numerics.rs`). |
| N18 | `polyroots(vec(…))` with clustered or repeated roots, such as coefficients for `(x-1)^6`. | Return roots with a documented error bound, or report unresolved conditioning. | The operation forwards floating coefficients to the generic complex-root iteration and has no residual/conditioning validation before returning roots (`core/src/numerics.rs:366–384`). |
| N19 | `dft(vec(1e308,1e308)) =` | Finite result or a clear overflow diagnostic. | Transform accumulation is unscaled; intermediate sums can overflow even where cancellation would produce a representable output (`core/src/numerics.rs`). |
| N20 | `idft(vec()) =` | Reject an empty transform explicitly. | The path computes `1.0 / n` for `n=0` and returns an empty result without a nonempty-input check (`core/src/numerics.rs`). |
| N21 | `rank(mat(1e-13,0;0,1))` | Rank 2, or a clearly documented relative-tolerance result. | Relative tolerance tied to the largest element classifies a nonzero pivot as zero (`core/src/linalg/mod.rs`). |
| N22 | `det(mat(1e-13,0;0,1))` | Approximately `1e-13`. | The same relative elimination tolerance can discard the small pivot (`core/src/linalg/mod.rs`). |
| N23 | `lsolve(mat(1e-13,0;0,1),vec(1e-13,1))` | `vec(1,1)`. | Pivot tolerance based on the largest matrix entry can reject a valid finite solution (`core/src/linalg/mod.rs`). |
| N24 | Determinant of a disconnected/zero-heavy dimensioned matrix such as `mat(1 m,0;0,1 s)`. | Reject physically ambiguous units or require an unambiguous row/column unit pattern. | Unit-pattern propagation seeds disconnected components as unitless and may assign arbitrary row/column dimensions (`core/src/linalg/mod.rs`). |
| N25 | `mat()` or `rows(mat())`. | Return a parse/evaluation error. | Empty matrix paths can index `rows[0]` while checking widths (`core/src/linalg/mod.rs`, `Array::of`/`matrix`). |

## Additional operation, evaluation, and modifier findings

| ID | Reproduction / affected operation | Expected behavior | Current gap / evidence |
|---|---|---|---|
| N26 | `normalcdf(1e308, -1e308, 1)`. | Reject overflow or return a well-defined tail probability. | `x - mean` overflows before standardization, producing an invalid CDF input (`core/src/numerics.rs`). |
| N27 | `normalquantile(1-1e-16,0,1)`. | Return the finite upper quantile corresponding to the supplied probability. | Probability arithmetic and the `1-p` tail transformation can round the requested probability to an endpoint, changing/rejecting the query (`core/src/numerics.rs`). |
| N28 | `normalquantile(1e-300,0,1)`. | Return a finite quantile near `-37`, or report that the requested tail is below the supported range. | The bisection interval is hard-coded to `[-40,0]` and has no explicit residual/range validation (`core/src/numerics.rs`). |
| N29 | `normalcdf`/`normalquantile` with non-finite known arguments. | Reject NaN/infinite x, mean, sigma, and probability consistently. | Checks enforce only `sigma > 0`; subtraction and quantile arithmetic can silently propagate non-finite values (`core/src/numerics.rs`). |
| N30 | `linterp` with large-offset knots whose decimal spacing survives as an exact rational but not as `f64`. | Either retain exact spacing or diagnose loss of resolution. | The public operation converts all samples and query positions to binary floats without a representability check (`core/src/numerics.rs`). |
| N31 | `linfit` with `y = 1e308 + small residuals`. | Stable centered fit or explicit loss-of-resolution error. | `y - y[0] - my` can overflow/round away residuals; only x centering and no finite intermediate check is used (`core/src/numerics.rs`). |
| N32 | `convolve(vec(1,2),vec(3,4),step: 1 s)`. | Validate the step's physical meaning and return output units including the sampling interval. | The step is simply multiplied into the vector after convolution; no dimension contract distinguishes sample units from signal units (`core/src/env.rs`, convolution path). |
| N33 | Discrete convolution with mixed zero dimensions, e.g. a dimensionless zero next to volt samples. | Permit zero as dimension-neutral or report a precise incompatible-sample error consistently with other reductions. | The fast numeric path requires every coefficient to have exactly the first coefficient's dimension, unlike `common_dimension`'s special zero handling (`core/src/linalg/mod.rs`). |
| N34 | `range(1e16,1e16+2,step:1)`. | Produce the two representable steps or reject a bound that cannot be represented faithfully. | `end-start` is computed after floating conversion and may become zero, yielding an empty or incorrect count (`core/src/env.rs`, `range`). |
| N35 | `range(0,1,step:-0.1)` and descending ranges with a positive step. | State and enforce a clear direction/termination contract. | The count is derived from `span` but there is no explicit check that step moves toward the end; invalid-direction ranges silently return empty vectors (`core/src/env.rs`). |
| N36 | `range(0, 0.9999999999, step: 1)` with an inclusive range. | Do not include `1`, because the endpoint is strictly below the next step. | The inclusive endpoint test adds a fixed `1e-9` tolerance before flooring, so it can include a step that is outside the requested bound (`core/src/env.rs:785–790`). |
| N37 | `at(vec(1,2), 0.0)` and `at(vec(1,2), 1/1)`. | Define whether mathematically integral numeric indices are accepted uniformly. | Index validation depends on `Num::as_int`; exact rational and float-integral forms can take different paths (`core/src/linalg/mod.rs`). |
| N38 | `cases(1, x, 2)` with a nonzero numeric condition and no explicit default. | Reject malformed branch structure or clearly define the final default syntax. | The parser chunks arguments in pairs and treats an odd final item as an unconditional default, which can hide a missing condition (`core/src/env.rs`). |
| N39 | `cases(value, condition, ...)` where the condition is a tiny nonzero float near numerical error. | Use a documented truth tolerance or reject an uncertain condition. | Conditions use exact `test != 0.0`; numerically uncertain comparisons can select a branch arbitrarily (`core/src/eval.rs`). |
| N40 | `assume(free_definition > 0)` where the name already has a symbolic definition. | Apply the assumption to the definition's free scalar names, as documented. | `sym_result` rejects any symbolic definition and tells the caller to assume its free names instead, without performing that substitution (`core/src/sheet.rs`). |
| N41 | `assume(x >= 0, x < 0)` in a single clause. | Report a contradiction before evaluation. | Parser-level sign intersection handles direct duplicate names, but equivalent constraints expressed through bound/defined names are not normalized together (`core/src/parse.rs`, `sheet.rs`). |
| N42 | `substitute(x,x)` or repeated constants in one clause. | Either preserve the request for diagnostics or reject duplicates. | Parsing silently deduplicates substitute names, so a malformed request is accepted with no indication (`core/src/parse.rs`). |
| N43 | `-> fraction` on a result containing irrational exact terms such as `sqrt(2)`. | Keep irrational terms exact and only rationalize representable rational coefficients. | The modifier is described as “exact fractions” but formatting policy can conflate fraction mode with a globally rational result; the contract does not distinguish irrational factors (`src/modifiers.typ`, `core/src/format.rs`). |
| N44 | Combine `digits(3), fraction` or `sci, eng`. | Reject incompatible display modes or define deterministic precedence. | Clause parsing permits combinations other than the explicit `expand`/`factor` conflict; later configuration assignments silently override one another (`core/src/sheet.rs`, `parse.rs`). |
| N45 | `factor` on an equation with a denominator root, e.g. `(x^2-1)/(x-1)=0`. | Preserve the excluded pole while presenting factored solution conditions. | Factoring/symbolic rendering exposes numerator roots; denominator restrictions are not consistently rendered in modifier output (`core/src/solve.rs`, `sheet.rs`). |
| N46 | Solve `sqrt(x)=x-2 -> solve(x)`. | Return only roots satisfying the original unsquared equation and domain. | Symbolic isolation can introduce roots; residual validation is only performed when substitution becomes fully numeric, so parameterized results can retain extraneous branches (`core/src/solve.rs`). |
| N47 | Numerically solve an equation with a tangent/even root, e.g. `(x-1)^2=0 -> solve(x)`. | Find the root despite no sign change. | The numerical scanner is primarily sign-change based; a root touching zero can be missed unless symbolic polynomial handling recognizes it (`core/src/solve.rs`). |
| N48 | `sin(x)=0 -> solve(x)` with a periodic function. | Return a bounded, explicit family or a documented “infinitely many roots” result. | Root scanning returns a finite sampled subset governed by scan limits, with no completeness contract for periodic equations (`core/src/solve.rs`). |
| N49 | Dimensioned polynomial solve with only one nonzero coefficient pair or inconsistent coefficient dimensions. | Reject inconsistent polynomial dimensions before solving, or infer dimensions from all terms. | `poly_dim` infers a variable dimension from only the first and last nonzero coefficients; intermediate terms can violate the inferred dimension (`core/src/solve.rs`). |
| N50 | `x^2 = a -> solve(x)` with a known negative real `a`, or with complex-valued `a`. | Return complex roots when the equation domain is complex, or clearly state real-only solve behavior. | Solve dispatch mixes symbolic complex quadratic roots with numerical real scanning; the selected branch depends on whether parameters are known, rather than an explicit solve-domain modifier (`core/src/sheet.rs`, `solve.rs`). |

## Suggested verification

The highest-risk items are N01–N05, N20, N25, N40, N45–N47 because they involve domain erasure, empty-input panic paths, documented modifier behavior, or missed/extraneous solutions. Each should become an independently named regression test after reproducing it against the current build. Numerical conditioning items should use exact/rational inputs where possible so the test distinguishes implementation loss from ordinary IEEE-754 limits.
